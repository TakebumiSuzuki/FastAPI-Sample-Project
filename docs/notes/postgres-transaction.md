# 【保存・復習用】SQLAlchemy × PostgreSQL 接続・MVCC 完全ガイド

---

### 第1章：コネクションとプロセスの仕組み
**（アプリとデータベースはどう繋がっているのか？）**

#### ① 初めてDBにアクセスする時（起動からコネクション取得まで）
1. **アプリ起動時:** SQLAlchemyの `Engine`（コネクションプール）が生成されますが、この時点ではまだPostgreSQLへのTCP接続は1本も張られておらず、空の状態で待機しています（遅延初期化）。
2. **リクエスト受信時:** FastAPI等の依存関係で `SessionLocal()` がインスタンス化されます。この時点でもメモリ上にSessionが作られただけで、まだコネクションは保持していません。
3. **最初のSQL実行時（遅延チェックアウト）:** 実際に `session.execute()` などSQL送信が必要になった瞬間に、SessionがEngine（コネクションプール）にコネクションを要求します。プールが空のため、EngineがPostgreSQLへTCP接続を要求し、PostgreSQL親プロセス（postmaster）が専用の **「バックエンドプロセス」を `fork()`** して接続が確立します。Sessionはその接続の参照を借り受けます。
4. この接続は、HTTPのような1回きりの通信ではなく、WebSocketのように **「繋ぎっぱなし（常時接続）」** になります。

#### ② 2回目以降のリクエストの時（すでに接続が確立している場合）
* 毎回プロセスをフォークすると重いため、使い終わった接続は切断せず、SQLAlchemyの **「コネクションプール」** に保管されています。
* 2回目以降は、新しいプロセスを作ることなく、**プール内で待機（`idle` 状態）している既存の接続をサッと取り出して使うだけ** なので、非常に高速に処理が始まります。

#### ③ バックエンドプロセスの性質
* **シングルスレッドで動く:** 1つのバックエンドプロセスは、複数の処理を同時にこなすことはせず、送られてきたクエリを **1つずつ順番に（同期的）** 処理します。
* **1つの状態しか持たない:** プロセスは「待機中（`idle`）」「クエリ実行中（`active`）」「トランザクション待機中（`idle in transaction`）」など、**常にどれか1つの状態** に確定しています。

### 第2章：トランザクションとMVCC（仮想XIDと本物XID）
**（読み取りと書き込みで裏側はどう動いているのか？）**

#### ① トランザクションの自動開始（Auto-begin）と状態把握
* SELECTであってもINSERTであっても、**「最初のSQLが実行される直前に、裏で自動的にトランザクションが開始（`BEGIN`）される」** という仕様になっています。実際にDBへ `BEGIN` を自動で送るのはDBドライバ（`psycopg`）で、SQLAlchemy（Session）はそれを前提に、`commit()` / `rollback()` 側を管理します（詳細は下のコラム）。
* **状態把握の仕組み（無駄打ちの防止）:** SQLAlchemyやDBドライバ（`psycopg`（psycopg3）等）は、メモリ上で「現在トランザクションが開いているか」を正確に追跡・管理しています。そのため、2回目以降のSQL送信時に無駄な `BEGIN` を毎回送信することは一切ありません。
* SELECT（読み取り）をするだけでも、DB側ではトランザクションが開いた状態になります。

> **💡 コラム：`BEGIN` を実際に送っているのは誰？（`autocommit=False` ＝既定の場合）**
>
> 前提：PostgreSQL・`psycopg`（psycopg3）・SQLAlchemy 2.x の組み合わせで、`autocommit=False`（既定）のとき。
>
> * **実際にDBへ `BEGIN` を送るのは `psycopg`（DBドライバ）。** SQLAlchemy ではない。SQLAlchemy公式ドキュメントにも「DBAPI（psycopg等）自体に `begin()` メソッドは無く、autobegin が実際に起きるのは DBAPI 側」と書かれている。
> * **`psycopg` は自分で状態を判断する。** PostgreSQLは各クエリの応答の最後に `ReadyForQuery` というメッセージを返し、そこに「いまトランザクション中か」の状態が入っている。`psycopg` はこの状態を見て、トランザクション外なら次のSQLの直前に `BEGIN` を自動で送る。**SQLAlchemyからの指令は不要。**
> * **SQLAlchemy の役割は「終わらせる側」。** `commit()` / `rollback()` / `close()` を呼ぶタイミングを管理する責任を持つ。ログに出る `BEGIN (implicit)` は SQLAlchemy 側の論理的な開始の記録であり、DBへ `BEGIN` を送った記録ではない。
> * **`with session.begin():` は DBの `BEGIN` とは別物ではなく、同じ1つのトランザクションの範囲をユーザーが明示するもの。** `with` ブロックを抜けるときに、正常なら `commit`、例外なら `rollback` が自動で呼ばれる。DBへ送る `BEGIN` は、これまで通り最初のSQLの直前に `psycopg` が送る（※「`session.begin()` 自体はDBへ何も送らない」点は公式ドキュメントからの推測で、実際のSQLログでは未検証）。
> * **ユーザーが `BEGIN` を書く必要はない。** ただし `commit()` は自分で呼ぶか `with session.begin():` を使う必要がある（忘れると変更は確定されない）。
>
> ```
> SQLAlchemy 側:  session.begin() ……………… with ブロックの終わりで commit / rollback
>                      │（最初のSQLが来るまで何も送らない）        │
>                      ▼                                          ▼
> psycopg 側:     最初のSQLの直前に BEGIN を送る → SQL → … → COMMIT / ROLLBACK
> ```
>
> ※ `autocommit=True` にした場合は `BEGIN` は自動では送られない（1文ごとにコミット）。

#### ② 「仮想XID」からスタートする賢い仕組み
* トランザクションが始まった瞬間、PostgreSQLは「この後、読み取りが来るか書き込みが来るか」をまだ知りません。
* そこで、**最初は全員とりあえず「仮想トランザクションID（Virtual XID）」という仮の番号** だけを渡してスタートします（本物の番号を節約するためです）。

#### ③ スナップショットと本物XIDへの昇格
* **スナップショットとは:**
  * その瞬間に「まだ処理中（未コミット）なトランザクションIDの一覧」などを記録した判定用データのことです。
  * データを丸ごとコピーするのではなく、この一覧と照合して「どのデータが確定済みで見える状態か」を判断するために使われます。
* **SELECT（読み取り）が実行されるとき:**
  * 実行直前に **スナップショット** を取得し、それを使って確定済みのデータだけを読み取ります。
  * データを読むだけで変更しないため、**「仮想XID」のまま** 処理を完了します。
* **UPDATE / INSERT（書き込み）が実行されるとき:**
  * まずスナップショットを使って、変更対象となる行を特定します。
  * そして、実際にデータを書き換えるまさにその瞬間に、**初めて「本物のトランザクションID（XID）」が発行され、昇格** します（変更された行のヘッダーに「誰が変更したか」を刻み込むためです）。

#### ④ 読み取りと書き込みのライフサイクル（いつ始まり、いつ終わるか）
* **読み取り（SELECT）の流れ:**
  1. 最初の `session.execute()` の直前に、裏で自動的にトランザクションが開始される。
  2. クエリの結果がアプリに返ってきても、**トランザクションは開いたまま（`idle in transaction`）維持** される。
  3. 最後に `session.close()` が実行されたときに、裏で `ROLLBACK` が発行されて **初めてトランザクションが終了する**。
* **書き込み（INSERT / UPDATE / DELETE）の流れ:**
  1. 最初の `session.execute()` の直前に、裏で自動的にトランザクションが開始される。
  2. SQLの実行結果が返ってきても、**トランザクションは開いたまま維持** される。
  3. `session.commit()` が実行された瞬間に、DBに変更が確定されて **トランザクションが終了する**（※その後さらにSQLを実行した場合は、新たなトランザクションが再度自動で始まります）。

### 第3章：データの転送（5000件のSELECTの場合）
**（DBからアプリへデータはどう運ばれるのか？）**

1. **DB側（バックエンドプロセス）:**
   * 5000件全部が揃うまでじっと待つのではなく、1行見つかるごとに **ネットワーク（TCP送信バッファ）へストリーミング（流し込み）** します。
   * ※DB側が勝手に「件数が多いから小分けにしよう」と自動判断して止めることはなく、通常クエリなら最速で全件を送信しようとします。
   * （※`ORDER BY` などの並び替えがある場合のみ、メモリ領域 `work_mem` に一旦溜めてソートします）
2. **ネットワーク間:**
   * 約1.5KBごとの **TCPパケットに自動的に小分け** にされて、ネットワーク上を流れます。
3. **アプリ側（SQLAlchemy / Python）:**
   * **デフォルトの動作（全件バッファリング）:** Pythonドライバは、小分けで届いたデータを **アプリのメモリ上で全部受け取り終えてから** 初めてアプリのコード（`Result`）に渡します。
     * ※何も対策せずに100万件などの巨大データをSELECTすると、アプリのメモリが枯渇（OOM: メモリ不足）してプロセスがクラッシュする原因になります。そのためWeb API等では通常 `LIMIT` / `OFFSET` 等で件数自体を制限します。
   * **大量データを小分けで処理したい場合:** アプリ側で明示的に **サーバーサイドカーソル（`yield_per()`）** を指定します。アプリから明示的に指示することで、裏側で `DECLARE CURSOR` / `FETCH` のSQLが使われ、DB側に結果を保持させながら1000件ずつ小分けで安全にフェッチできます。

### 第4章：リクエスト終了と `db_session.close()` の本当の役割
**（なぜレスポンスの後に `db_session.close()` を呼ぶのか？）**

FastAPIなどでレスポンスを返した直後、`finally` ブロックで **`db_session.close()`** が実行されます。

#### `db_session.close()` が裏でやっている4つのこと
1. **アプリ側メモリの整理:**
   * Pythonの Session オブジェクトをリセットします。
2. **DBへ終了のSQLを送信（ここが超重要！）:**
   * 読み取り（SELECT）しかしておらず `commit()` を呼んでいなくても、トランザクションは開いたまま（`idle in transaction`）になっています。
   * そのため、SQLAlchemyは裏でDBへ **`ROLLBACK`** を送信し、**「何も変更せずにトランザクションを安全に終了してください」** と伝えます。
3. **DB側の状態リセット:**
   * バックエンドプロセスはトランザクションを閉じ、綺麗な待機状態（**`idle`**）に戻ります。
4. **接続をプールへ返却:**
   * PostgreSQLとの **TCP常時接続は切断せず生かしたまま**、SQLAlchemyのコネクションプールへ戻します（次のリクエストが来たら、そのまま再利用されます）。

### 全体の要約表

| 項目 | 初回アクセス時 | 2回目以降（通常時） |
| :--- | :--- | :--- |
| **コネクション** | 新規にTCP常時接続を確立 | プール内の既存コネクションをそのまま再利用（チェックアウト） |
| **DBプロセス** | 親プロセスがバックエンドプロセスを `fork()` | 接続に対応する既存のバックエンドプロセスがそのまま待機・処理 |
| **トランザクション開始** | 最初のSQL実行時に自動 `BEGIN`（**仮想XID** 発行） | 同左 |
| **読み取り（SELECT）** | スナップショット取得、**仮想XID** のまま実行 | 同左 |
| **書き込み（UPDATE等）** | 変更の瞬間に **本物のXID** を発行して行に刻む | 同左 |
| **リクエスト終了時** | `db_session.close()` で `ROLLBACK` 送信 ➔ 接続をプールへ保管 | `db_session.close()` で `ROLLBACK` 送信 ➔ 接続をプールへ返却 |

### よくある質問（Q&A）

#### Q1. 仮想トランザクションID（仮想XID）は、MVCCの機能に関与しないのですか？
* **A.** はい、MVCC（データの新旧バージョン管理）には関与しません。
* データ行に刻印されて可視性（見える/見えない）の判定に使われるのは「本物XID」だけです。仮想XIDはデータ行には書き込まれず、ロック管理やプロセス識別といったDB内部の制御用途でのみ使われます。

#### Q2. トランザクションID（仮想・本物）は、クライアント側ではなくDBプロセスの中だけに置かれるのですか？
* **A.** はい、DB側（PostgreSQLプロセスや共有メモリ）の中だけで保持・管理されます。
* クライアント側（SQLAlchemy / Pythonアプリ）のメモリにIDそのものが渡されたり保持されたりすることはありません。

#### Q3. トランザクション中かどうかは、クライアント側も知っているのですか？
* **A.** はい、クライアント側は正確に把握しています。
* トランザクションID番号そのものは知らなくても、DBドライバ（`psycopg`）は、サーバーが各クエリの応答の最後に返す `ReadyForQuery` メッセージから「現在トランザクション中か」を把握しています。SQLAlchemyもメモリ上で「現在トランザクションを開いている状態（`in transaction`）である」という状態フラグを管理・追跡しています。

#### Q4. トランザクション分離レベルとは何ですか？変更すると何が変わるのですか？
* **A.** 同時に動く複数のトランザクション同士が、互いの変更をどれくらい見えないように隔離するか（安全性の強さ）を決める設定です。
* 分離レベルを変更すると、**「スナップショットを取得するタイミング」** と **「同じトランザクション内でのデータの見え方」** が変わります。

| 分離レベル | スナップショット取得タイミング | 同じ処理内でのデータの見え方 |
| :--- | :--- | :--- |
| **Read Committed<br>（PostgreSQLデフォルト）** | **SQLを実行するたび** に毎回新しく取得 | 途中で他人がコミットすると、2回目のSELECTで新しいデータが見える |
| **Repeatable Read** | **初回クエリ時に1回だけ** 取得して使い回す | 途中で他人がコミットしても、最初と同じデータが見え続ける |
| **Serializable** | 初回クエリ時に1回取得（＋依存関係を監視） | 最初と同じデータが見え、矛盾が起きそうなときは競合エラーで止める |

### 第5章：スナップショット・行の可視性・vxid/xidの一生
**（BEGINからCOMMITまで、DBサーバーの中で何が起きているか）**

#### ① 場面設定
1つのSessionで、`execute①(SELECT)` → `execute②(UPDATE)` → `execute③(SELECT)` → `commit()` という順にSQLが実行されるケースを例に、クライアント側とDBサーバー側（バックエンドプロセス）で何が起きているかを順番に追う。

#### ② execute①の瞬間（BEGINとほぼ同時）
* `psycopg` は「まだトランザクションが始まっていない」ことを把握しているので、`execute()` の直前に裏で自動的にBEGINを一緒に送る（autobegin）。SQLAlchemyが指令を出すわけではない。つまりBEGINのタイミングは、実質execute①のタイミングとほぼ同時。
* BEGINを受けたバックエンドプロセスは、この瞬間に **vxid（仮想トランザクションID）** を発行する。「バックエンドプロセス番号＋そのプロセス内でのローカルな連番」というペアの数字で、そのプロセスの中だけで完結する管理用の番号。
* 続けてexecute①（SELECT）を処理するために、この瞬間に **スナップショット** も取得する（xmin・xmax・xip_listの3つ組）。
* execute①は読み取りなので、**xid（本物のトランザクションID）** はまだ発行されない。
* これらはすべてバックエンドプロセス自身がその場で作り出すものであって、クライアントから送られてくるものでも、結果として送り返されるものでもない。クライアントに返るのはSELECTの結果行だけ。

#### ③ execute②の瞬間（書き込み文の場合）
* 同じトランザクションの続きなので、vxidは発行し直さず、②で発行済みのものをそのまま使う。
* スナップショットはSQL文ごとに取り直すルール（デフォルトのREAD COMMITTEDの場合）なので、ここでも新しいスナップショットを取得する。
* execute②が書き込み（UPDATEなど）だった場合、**この瞬間に初めてxidが発行される**。もしexecute①が書き込みだったら、xidが発行されるタイミングはexecute①の時点にずれる。読み取りしかしないトランザクションなら、最後までxidは発行されない。

#### ④ execute③〜commit()
* execute③でもvxid・xid（発行済みなら）はそのまま使い続け、スナップショットだけ新しく取り直す。
* `commit()` が呼ばれると、バックエンドプロセスはxidを **CLOG（コミットログ）** に「committed」として記録する。この番号は今後二度と使われない。
* vxidは役目を終えて解放され、同じバックエンドプロセスが次のトランザクションを始めるときに番号を使い回して再発行する。
* スナップショットはそもそもSQL文ごとの使い捨てなので、特に何も残らない。

#### ⑤ クライアント側から見えるもの
* snapshot・vxid・xidの値そのものは、クライアント（SQLAlchemy Session／Pythonのメモリ）には一切渡らない。SQLAlchemyが把握しているのは「今トランザクションを開いているかどうか」というフラグだけ。
* 例外的に `SELECT txid_current()` のような専用の関数を明示的に実行すれば値自体を取得することはできるが、これは通常のexecute()の結果には含まれない。

#### ⑥ vxidとxidの違い

| | vxid（仮ID） | xid（本物ID） |
| :--- | :--- | :--- |
| 発行タイミング | BEGIN時に即座に発行 | 最初の書き込み文の瞬間に発行（読み取り専用なら最後まで発行されない） |
| 番号の性質 | バックエンドプロセス番号＋ローカル連番のペア | DB全体で一本のグローバル連番 |
| MVCCの可視性判定 | 使われない（ロック管理pg_locksで使用） | xmin/xmax/xip_listに使われるのはこちら |
| 終了時の扱い | 解放され、同じプロセスの次のトランザクションで使い回される | CLOGにcommitted/abortedとして永続記録され、番号は二度と再利用されない |

#### ⑦ 行の可視性判定（スナップショットの使われ方）
各行は隠しシステム列 `t_xmin`（挿入したトランザクションのxid）と `t_xmax`（削除したトランザクションのxid、まだ削除されていなければ0）を持っている。あるxidが「スナップショットから見て確定済み（コミット済み）」かどうかは次のように判定する。

* `xid < snapshot.xmin` → 確定済み（スナップショット取得時点でとっくにコミット/アボート済み）
* `snapshot.xmin ≦ xid < snapshot.xmax` かつ `xip_listに含まれない` → 確定済み（スナップショット取得より前にコミットされた）
* `xip_listに含まれる`、または `xid ≧ snapshot.xmax` → 未確定（進行中、またはスナップショット取得後に始まった）

行が可視になるのは「挿入者（`t_xmin`）が確定済み」かつ「未削除（`t_xmax`=0）、または削除者（`t_xmax`）が未確定」のとき。例えば `xmin=101, xmax=106, xip_list={101,103,104}` というスナップショットなら、挿入者が90番の行は確定済みなので見え、挿入者が103番（xip_list内）の行はまだ見えない、削除者が102番（確定済み）の行は削除済み扱いで見えない、削除者が104番（xip_list内）の行はまだ削除が反映されておらず見える、といった判定になる。

#### ⑧ 書き込み時の特別な挙動
UPDATE/DELETEも⑦と同じ可視性判定で対象行を選ぶが、対象行の削除者（`t_xmax`）がxip_list中（＝今まさに別のトランザクションが更新/削除中）だった場合は、そのトランザクションの終了を待つ。相手がロールバックすれば普通に処理を続け、コミットすれば（READ COMMITTEDでは）その行の最新版を取り直してWHERE条件を再評価する。
