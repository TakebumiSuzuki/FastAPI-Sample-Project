# 20. `async def` と `def` の使い分け

## 1. この章の目的と全体像

第20章では、第21章で DB アクセスを非同期（`AsyncSession`）へ移行する前段階として、**uvicorn・イベントループ・FastAPI・スレッドプールの関係**と、**`async def` / `def` をどう使い分けるべきか**の仕組みを整理した（コード変更はなく概念の理解と設計判断の章）。

```text
[クライアントからのリクエスト]
  │
  ▼ ① OSのソケットキュー（backlog=2048。イベントループが忙しければここで待つ）
[MainThread: uvicorn が asyncio イベントループ (_run_once) を回す]
  │  受信したリクエストごとに loop.create_task() で1タスクを作成
  ▼ ② イベントループ内の実行待ちキュー (_ready) に積む
[Task 実行: await app(scope, receive, send) で FastAPI 本体を呼ぶ]
  │
  ├── (A) エンドポイント / Depends が `async def` の場合
  │        └── 別スレッドは作らず、同じ MainThread 上でそのまま直進して await 実行
  │             ├── 非同期I/O待ち (await) に到達 ──> 一時停止し、イベントループへ制御を返す
  │             └── 同期の重い処理・同期I/O ───────> 終わるまでイベントループ全体が完全停止
  │
  └── (B) エンドポイント / Depends が `def`（async なし）の場合
           └── run_in_threadpool (AnyIO WorkerThread: デフォルト上限40スレッド) へ切り出す
                └── 関数を渡した直後に Future を await し、即座にイベントループへ制御を返す
```

## 2. Q&A（学習中の疑問と解決まとめ）

### Q1. FastAPI 自体が `asyncio` のイベントループを動かしているのか？
**A.** イベントループを立ち上げて回している主役は **uvicorn**（`Server.run` 内の `asyncio_run`）。
- `app = FastAPI()` 本体は「常駐する1つのタスク」ではなく、`async def __call__(self, scope, receive, send)` を持つ**巨大な非同期 callable（呼び出し可能）オブジェクト**。
- uvicorn は **HTTP リクエストが1件届くたびに** `self.loop.create_task(self.cycle.run_asgi(app))` で新しいタスクを1つ作り、その中で `await app(...)` を呼び出し、レスポンスを返したらそのタスクは終了する。

### Q2. `app = FastAPI()` を呼ぶときに非同期と同期を選べるのか？
**A.** `app` 自体は `async def __call__` の1種類しかなく、**uvicorn からは常に非同期（`await app(...)`）でしか呼ばれない**。
- 非同期か同期かが分かれるのは、`app` の内部（`fastapi/routing.py` の `run_endpoint_function`）で**各エンドポイント関数を呼ぶ瞬間**。
- FastAPI は `_is_coroutine_callable(dependant.call)` でエンドポイント関数が `async def` か `def` かを判定している：
  - **`async def` の場合**：同じスレッド（イベントループのスレッド）のまま `await dependant.call(**values)` で直接呼ぶ。
  - **`def` の場合**：`await run_in_threadpool(dependant.call, **values)` を呼び、標準ライブラリの `threading.Thread` を継承した AnyIO の `WorkerThread`（スレッドプール）で実行する。
- なお、`Depends`（依存関数）も `solve_dependencies` 内で全く同じルールで判定・実行される。

### Q3. プロセスの中のスレッドは「木構造（親子関係）」になっているのか？
**A.** **木構造ではなく、すべて横並び（フラット）**。
- プロセス起動時に最初の1本として `_MainThread`（メインスレッド）が必ず1つ作られる。
- ただし、OSのプロセス（明確な親子ツリーを持つ）とは異なり、スレッドには親子の階層構造はない。どのスレッドから作られたかにかかわらず、すべてのスレッドはプロセス直下の辞書 `threading._active` にフラットに管理され、作った側のスレッドが先に終了しても作られたスレッドはそのまま動き続ける。

### Q4. リクエストが殺到したとき、どこにキューがあり、どう順番待ちするのか？
**A.** 2段階のキューと、`async def` / `def` それぞれの挙動がある。
1. **OSのソケットキュー**：uvicorn は `loop.create_server(..., backlog=config.backlog)` で通信窓口を開いている。イベントループが前の処理で手一杯の間は、届いたリクエストはまずOS側のソケットキューに溜まり、イベントループの `_selector.select()` が回ってきたタイミングで読み出される。
2. **イベントループの `_ready` キュー**：uvicorn が `create_task()` を呼ぶと、イベントループ内の FIFO キュー `self._ready` にタスクが積まれ、CPU（イベントループ）の手が空いた順に `app` が実行される。そのため、CPUが忙しければ uvicorn が `app` を実行し始めること自体も待たされる。
3. **`app` の中で `async def` エンドポイントに出会ったとき**：`await dependant.call(...)` しただけでは新しく `_ready` キューに積み直されるわけではなく、同じタスクのまま直進して関数内を実行する。その奥で**実際の非同期I/O待ち（未完了の `Future`）にぶつかった瞬間**に初めて一時停止し、イベントループへ制御を戻す。
4. **`app` の中で `def` エンドポイントに出会ったとき**：`run_sync_in_worker_thread` が呼ばれ、待機中のスレッド（`idle_workers`）がなければその瞬間に `WorkerThread` を新規作成・起動し（10秒以内に空いたスレッドがあれば再利用）、関数を渡した直後に `return await future` を実行する。これにより**即座にI/O待ちと同じ扱いで一時停止し、イベントループへ制御が返される**。

### Q5. すべて `async def` で書いた場合、1スレッドで完結するのか？ 5msごとのスレッド切り替えは起きるのか？
**A.** すべて `async def`（内部ライブラリ含む）で統一すれば、ワーカースレッドは1つも作られず **`MainThread` の1本だけで完結する**。
- Python の「5msごとの切り替え（`sys.getswitchinterval() == 0.005`秒）」は、**同じプロセス内にGIL（Global Interpreter Lock：Pythonコードを同時に1スレッドしか動かさないための鍵）を待っている別スレッドが存在するとき**にだけ起きる仕組み。
- そのため、すべて `async def` で1スレッドしかなく、OS上で同じCPUコアを奪い合う他の重いプロセスもいなければ、**5msごとのコンテキストスイッチすら発生せず、1つのCPUが余計な切り替え作業を挟まずに黙々とイベントループの作業に集中できる**。
- 逆に、この1スレッドの状態で `async def` の中に**同期の動画変換や重い計算・同期I/O（`await` なし）**を書いてしまうと、勝手に別スレッドへ逃げてはくれないため、その処理が終わるまで**イベントループ全体が完全ストップ（他の全リクエストの受付・処理が停止）**する。

### Q6. `def`（同期）で書いた場合、複数スレッドになっても効率性は保たれるのか？
**A.** スレッド切り替えのオーバーヘッドやスレッドごとのメモリ消費はあるものの、**実用上十分な効率性が保たれる**。
- **Python計算中**：複数スレッドが同時にPythonコードを動かそうとすると、GILの仕様により最大5msごとにコンテキストスイッチが発生し、別スレッドがGILを握っている間はイベントループのスレッドも少し待たされる。
- **同期I/O待ちに入った瞬間**：DB通信やファイル読み書き、ソケット通信などのI/O待ちに入る瞬間、Python内部のCコードは **5msを待たずに `Py_BEGIN_ALLOW_THREADS`（`PyEval_SaveThread`）で即座にGILを手放し**、OSもそのスレッドを即座に待機（スリープ）状態にしてイベントループや他のスレッドへCPUを切り替える。
- さらに、`def` であればうっかり同期処理を書いてもイベントループ全体が止まる事故が起きないため、安全・気楽に書けるメリットがある。

### Q7. では、どういうアプリなら `async def` が必須・最適で、どういうアプリなら `def`（同期）で問題ないのか？
**A.** スレッドプールの同時上限（`CapacityLimiter(40)` のデフォルト **40スレッド**）と、I/O待ち時間の長さで決まる。

| 方式 | 向いているケースと理由 |
| :--- | :--- |
| **`async def` が最適・必須** | **① チャットボット（LLMの completion 待ち等で1リクエスト数秒〜数十秒待つ）**<br>**② リアルタイム通信（WebSocket のゲーム・チャット等：`get_websocket_app` は `async def` 専用）**<br>**③ ストリーミング配信（SSE / `EventSourceResponse` 等で接続を繋ぎっぱなしにする）**<br>**④ 1リクエスト内で複数の外部APIを同時に叩くアプリ・超高頻度アクセスAPI**<br>→ 1プロセス・同期（`def`）で常時接続ゲームやストリーミングを作ると、**40人が繋いだ時点で40スレッド全てが埋まり、41人目は誰かが抜けるまでプレイ（接続）できなくなる**。また、マルチプロセス（`uvicorn --workers N`）にするとプロセスごとにメモリを丸ごと複製するため、何千本もの長時間I/O待ちを抱える用途では、1スレッド・最小メモリで何千件も同時に待てる `async def` が圧倒的に有利。 |
| **`def`（同期）で十分なケース** | **外部通信がなく、アプリ内部（自前）のDBへの読み書きだけで済む通常のWebアプリ**<br>1. **1回のI/Oが一瞬で終わる**：内部DBへの読み書きは1回数ms〜十数msで完了してすぐスレッドが空くため、40スレッドを使い切る前に次々と回転する。<br>2. **DB側の同時接続枠の方が先に上限になる**：そもそも SQLAlchemy の接続プール（DBと繋ぐパイプの数）自体が、`QueuePool.__init__` のデフォルトで常時5本（`pool_size=5`）＋一時追加10本（`max_overflow=10`）＝**最大15本**に絞られている。つまりDBアクセスしかしないアプリでは、40スレッドを使い切るより前に「DBの15枠待ち」になるため、同期（`def`）で何の問題もない。 |

### Q8. 今のプロジェクト（19章時点）で、関数定義だけ `async def` に変えてはいけない理由は？
**A.** 現在使っている SQLAlchemy の `Session` は**同期I/O**だから。
- 中身を同期 `Session` のまま、エンドポイント（`routes/users.py` 等）や `Depends`（`deps.py` の `get_db_session` / `get_user`）の宣言だけ `async def` に変えると、スレッドプールに切り出されなくなり、イベントループの1スレッド上で同期DB通信を実行してイベントループをブロックする事故になる。
- そのため、現状の同期 `Session` を使う限り `def` が正解であり、次の第21章で `AsyncSession` と非同期DBドライバ（`aiosqlite`）へ置き換えることで初めて `async def` へ移行できる。
