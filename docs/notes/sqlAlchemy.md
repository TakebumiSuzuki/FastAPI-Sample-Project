# SQLAlchemy 2.0 モデルクラスの裏側の仕組み

SQLAlchemy 2.0において、モデルクラスに `name: Mapped[str]` と記述するだけで、なぜデータベース定義、インスタンス化、そして型推論がすべて魔法のように成立するのか。その裏側の仕組みを整理する。

## 1. なぜ `__init__` を書かなくてよいのか？
開発者が自分で `__init__` を書かなくてもインスタンス化できるのは、SQLAlchemyの基底クラス（`DeclarativeBase`）が、インスタンス化の際の**キーワード引数（`**kwargs`）を受け取って対応する属性にセットする汎用的な `__init__` を自動で提供している**からである。

これにより、`User(name="Alice")` のようにカラム名をそのまま渡すだけで、よしなに値をセットしてくれる。

## 2. 実行時：型ヒントを読み取ってテーブルを作る
Python本体は「実行時に型ヒントを強制しない（無視する）」という性質を持つが、SQLAlchemyはこの仕様を逆手に取っている。

クラスが読み込まれた瞬間（起動時）、SQLAlchemyはクラスの `name: Mapped[str]` という型情報を読み取る。そして**「なるほど、データベース上には文字列型のカラムが必要なんだな」と解釈し、裏側で自動的にテーブル定義（`Column`）を構築**している。これが `Mapped[ ]` で包まなければならない最大の理由である。

## 3. ディスクリプタの魔法：アクセス元で振る舞いが変わる
モデルクラスに定義した `name: Mapped[str]` は、クラス定義が読み込まれた瞬間にフック（メタクラス等の仕組み）によって**「ディスクリプタ（アクセスを制御するプロキシ・特製オブジェクト）」**に即座に上書き（オーバーライド）される。

この「賢い門番（プロキシ）」が属性アクセスを仲介し、誰がアクセスしてきたかによって返すものを切り替えている。

* **クラスから呼ばれた場合（`User.name`）**
  * ディスクリプタは「クラスからのアクセス」と判断し、**クエリ構築用の内部オブジェクト**を返す。（例：`User.name == "Alice"` という条件式が作れる）
* **インスタンスから呼ばれた場合（`user = User(); user.name`）**
  * ディスクリプタは「インスタンスからのアクセス」と判断し、**実際の値（`"Alice"` という `str`）**を返す。

## 4. 静的型チェッカーはどうやってこれを見抜いているのか？
実行前の型チェッカー（Mypyなど）が「インスタンスからは `str` が返り、クラスからは `内部オブジェクト` が返る」と理解できるのは、**SQLAlchemyの `Mapped` 型の中に「アクセス元に応じた戻り値のルール」が定義されているから**である。

```python
# Mapped型の内部定義のイメージ
class Mapped(Generic[T]):
    @overload
    def __get__(self, instance: object, owner: type) -> T: ...
    # ↑ インスタンスから呼ばれたら T (strなど) を返す

    @overload
    def __get__(self, instance: None, owner: type) -> InstrumentedAttribute[T]: ...
    # ↑ クラスから呼ばれたら 内部オブジェクト を返す
```
