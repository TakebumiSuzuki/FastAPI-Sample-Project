# PyJWT（JWT）の仕組みと Flask-Login / セッション Cookie 認証との比較

## 1. JWT（RFC 7519）と PyJWT の仕組み

**PyJWT** は、国際標準規格である **JWT（RFC 7519）** のルールに従ってトークンの生成（`encode`）と検証・復元（`decode`）を行うライブラリ。

### トークンの構造とエンコードの流れ
JWT は `[ヘッダー].[ペイロード（辞書データ）].[署名]` の3つを `.` で繋いだ文字列。

1. **ヘッダーとペイロードの変換（Base64URL エンコード）**
   ```text
   Pythonの辞書 -> JSON文字列 -> UTF-8バイト列 -> Base64URL文字列
   ```
   - URL や HTTP ヘッダーで安全に送れる英数字・記号に書き直しているだけで**暗号化ではない**（秘密鍵を知らない第三者でも中身を読める）。
2. **署名の生成と検証（ハッシュ計算）**
   ```text
   [変換したヘッダー].[変換したペイロード] ＋ 秘密鍵 ──(HMAC-SHA256等のハッシュ計算)──> [署名]
   ```
   - デコード時は秘密鍵で署名を再計算して照合し、中身が1文字でも書き換えられていないか（および期限切れでないか）を検証する。

## 2. ペイロードの標準キー（登録済みクレーム）と設計の注意点

RFC 7519 では以下の7つが標準キーとして定義されている（すべて任意）。

- **`sub`** (Subject)：対象の識別子（ユーザーIDなど）
- **`exp`** (Expiration Time)：有効期限
- **`jti`** (JWT ID)：トークン固有のID（使い回し防止・無効化管理用）
- **`iat`** (Issued At)：発行日時
- **`nbf`** (Not Before)：有効開始日時
- **`iss`** (Issuer)：発行者
- **`aud`** (Audience)：利用対象

### 独自キー（`role` など）を入れる際の注意
一度発行した JWT は有効期限（`exp`）が切れるまで書き換えられない。DB 側で権限（`role`）を変更・剥奪しても期限切れまで古い権限が通ってしまうため、即時反映が必要な場合は JWT に `role` を入れず都度 DB を参照する。

## 3. アクセストークン・リフレッシュトークンと保存場所

- **リフレッシュトークンは JWT の規格外**：アクセストークン／リフレッシュトークンの使い分けは **OAuth 2.0（RFC 6749）** の概念であり、JWT 自体は単なるデータ形式。両方を JWT で作る場合はペイロードに `"type": "access"` / `"refresh"` などを入れ、アプリ側のロジックで区別する。
- **配置パターン①（メモリ ＋ Cookie）**：
  - アクセストークン（短命）をフロントのメモリ、リフレッシュトークン（長命）を `HttpOnly` Cookie に置く（XSS によるトークン窃取対策）。
- **配置パターン②（アクセストークンのみを Cookie に保存）**：
  - リフレッシュトークンを使わず、寿命を長めにしたアクセストークン1つだけを `HttpOnly` Cookie に入れる構成も実務でよく使われる（自動送信されるため `SameSite` 属性による CSRF 対策が前提）。

## 4. Flask-Login（`itsdangerous`）と PyJWT / FastAPI の比較

### 本質的な共通点
Flask-Login（および Flask 標準セッション）も、「ユーザーID等の辞書を Base64URL 変換し、秘密鍵のハッシュ署名をつけて `HttpOnly` Cookie でやり取りする」という点で、上記の「パターン②」と仕組みはほぼ同じ。

### なぜ Flask は JWT ではなく独自方式（`itsdangerous`）なのか
1. **時期のズレ**：Flask と `itsdangerous` の誕生（2010年）の方が、JWT の国際標準化（2015年）より5年早かったため。
2. **用途の違い**：他言語・他社サーバー間での連携を想定した「国際パスポート（JWT）」に対し、同じサーバー内だけで完結する Cookie には暗号方式ヘッダー等を省いた軽量な「自分用の控え券（`itsdangerous`）」で十分だったため。

### なぜ PyJWT（FastAPI）の方が複雑に見えるのか

| 項目 | Flask-Login（＋Flask標準セッション） | PyJWT（＋FastAPIで自前実装） |
| --- | --- | --- |
| 役割 | **認証管理の全部入りパック** | **トークン変換だけの単機能部品** |
| 署名・検証 | 自動（裏で `itsdangerous` が実行） | 自分で `jwt.encode` / `decode` を呼ぶ |
| Cookie 読み書き・期限 | 自動（設定値で1週間などに変更可） | 自分でヘッダーや Cookie から出し入れする |
| ユーザー取得 | `@user_loader` を登録すれば自動 | 自分で `Depends` を書いて DB から取得する |

### FastAPI で Flask-Login と同じ仕組みを使う方法
FastAPI の土台である **Starlette** には標準で `SessionMiddleware` があり、その内部では Flask と同じ `itsdangerous` が使われている（オプション依存のため利用時は `uv add itsdangerous` が必要）。
`SessionMiddleware` で `request.session["user_id"]` を読み書きし、DB からユーザーを取得する関数を `Depends` で1つ定義すれば、FastAPI でも Flask-Login とほぼ同じ実装ができる。
