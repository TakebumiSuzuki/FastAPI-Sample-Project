# SQLAlchemy Session and Transaction Management Note

## 1. Session Settings
- **`autocommit=False` (Recommended)**: Requires explicit `db.commit()` to finalize transactions, preventing accidental uncommitted changes and maintaining data integrity.
- **`autoflush=False` (Recommended)**: Prevents automatic memory-to-DB flushing before queries. Gives explicit control over when changes are pushed to the database.

---

## 2. When to Use `db.flush()`
`db.flush()` sends pending SQL commands (`INSERT`/`UPDATE`/`DELETE`) to the DB within the current transaction without committing them.

### Typical Use Cases
1. **Retrieve Auto-generated IDs**: Obtain Primary Keys generated by DB (`AUTO_INCREMENT`) before creating child records.
2. **Early Constraint Checking**: Catch `IntegrityError` (e.g., UNIQUE constraint violation) early in a `try-except` block before full commit.
3. **Retrieve Server Defaults**: Access DB-generated values like `created_at` timestamps.

---

## 3. Transaction & Locking Mechanics

### Transaction Lifecycle (Lazy Begin)
- **Session creation**: Does NOT start a DB transaction.
- **First DB operation** (`SELECT`, `flush()`, etc.): Automatically triggers `BEGIN` under the hood.
- **`db.commit()` / `db.rollback()`**: Finalizes and closes the transaction.

### Locks and MVCC
Modern RDBMS follow the rule: **"Readers don't block writers, writers don't block readers, but writers block writers."**

| Operation | Lock Type | Behavior & Waiting Mechanism |
| :--- | :--- | :--- |
| **`SELECT` (Read)** | **No Lock** | Uses **MVCC** (Multiversion Concurrency Control) to read snapshot versions. **Zero wait time**. *(Except explicit `FOR UPDATE`)* |
| **`INSERT` / `UPDATE` / `DELETE` / `flush()` (Write)** | **Exclusive Lock (Row Lock)** | Locks the targeted rows. **Other writers must wait** until `commit()` or `rollback()`. |
